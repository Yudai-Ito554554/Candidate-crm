# Fable 5 再照会: S3-3（viewerのURL直接入力）の検証方式

作成日: 2026-08-19
対象: `docs/production-go-no-go-checklist.md` S3-3
基準コミット: `b8c5f8f`

## 要旨

Q2（`docs/fable5-design-batch6a-and-cross-cutting-2026-08-15.md` 29-39行）で指定された **「web buildをブラウザで起動し、viewerアカウントでURLバーから編集6ルートを直打ちする」方式が、このコードベースでは成立しない**ことが判明した。指定の前提が実装と食い違っているため、方式の再決定をお願いしたい。

不成立の理由は「viewerが編集画面を開けてしまう」ではない。**編集画面は開けないが、その理由がロール制御ではなく未ログインになるため、S3-3の証跡として使えない**という問題である。

## 指定された方式とその前提

> このアプリはTauriでもブラウザでも同一のReact SPAなので、**web buildをstagingへ向けてブラウザで起動し、viewerアカウントでURLバーから編集6ルートを直打ちする**のが「URLを直接入力する」の忠実な再現であり、production配布物へdeep-link攻撃面を一切増やさない。

前提は「Tauriでもブラウザでも同一のReact SPA」である。UI層とルーティング層についてはそのとおりだが、**認証セッションの永続化層は同一ではない**。ここが崩れている。

## 崩れている前提（コード参照）

### 1. ブラウザではページの完全リロードでセッションが必ず失われる

- `src/lib/supabase.ts:19` — Supabaseクライアントを `persistSession: false` で生成している（`detectSessionInUrl: false` も同様）。ブラウザのstorageにはセッションが一切保存されない
- `src/features/auth/secure-session.ts:9-11` — セッション復元は `isTauriRuntime()`（`window.__TAURI_INTERNALS__` の有無）で分岐し、`invokeCredential()`（同 19-25行）はTauri外では `TauriRuntimeUnavailable` を投げる。復元経路はOS資格情報ストア（Keychain / 資格情報マネージャー）へのTauri IPCのみ
- `src/features/auth/auth-provider.tsx:61-67` — 初期状態はこの `bootstrapSecureSession()` の結果が持つ（`INITIAL_SESSION` は同 47行で意図的に無視）。ブラウザでは常に `null` が返り `unauthenticated` になる
- `src/features/auth/secure-session.ts` の該当コメント — 「資格情報ストアのフォールバックとしてlocalStorage永続化を復活させることはしない」と明記。Batch 5の設計判断であり、ブラウザに代替の復元経路は**設計上存在しない**

URLバーへの直接入力はSPA内遷移ではなく**完全なページロード**なので、この経路を必ず通る。したがってブラウザではviewerに限らず**全ロールが未ログイン状態で着地する**。

### 2. 未ログイン着地後、要求したルートへは戻れない

- `src/features/auth/protected-route.tsx:16` — `if (!auth.session) return <Navigate replace to="/login" />;`。**遷移元を保持していない**（`state` も `redirect` クエリもなし）
- `src/pages/login-page.tsx:34` / `:44` / `:72` — 認証済みになると常に `"/"` へ遷移する。復帰先を受け取る口がない

結果として、URLバーに `/candidates/c-001/edit` を入力しても、観測されるのはログイン画面であり、ログイン後に到達するのはホーム（`/`）である。**要求した編集ルートは一度も評価されない。**

### 3. よって証跡にならない

S3-3が確認したいのは「viewerでは編集ルートがロールにより拒否される」ことだが、上記の経路では**未ログインによる拒否**しか観測できない。両者は区別できず、viewerロール固有の制御を実証したことにならない。

## 成立していれば観測されるはずのもの（参考）

編集ルートに到達できた場合、`src/features/access/editor-route.tsx:18-35` は**リダイレクトせず**、`role="alert"` の「閲覧専用アカウントです」パネルを表示し、送信ボタンを描画しない。つまりS3-3の合格観測は「ログイン画面が出る」ではなく「このパネルが出て、かつ送信ボタンが存在しない」である。

一次証跡としては既にこれを自動テストで押さえている。

- `src/pages/app-routes.test.tsx:2811-2844` — 編集7ルート（`/candidates/new`, `/candidates/import`, `/candidates/:id/edit`, `/jobs/new`, `/jobs/:id/edit`, `/companies/new`, `/companies/:id/edit`）を `it.each` で直接renderし、`viewer` ロールで上記パネルの表示と送信ボタンの不在をassertしている

なお、チェックリストS3-3の記述は「6ルート」だが、自動テストは `/candidates/import` を含む**7ルート**を対象にしている。UAT対象を6とするか7とするかも併せて確定したい。

## 検討した選択肢

| 案  | 内容                                                                                                | 評価                                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | ログイン後に要求ルートへ復帰する実装を追加（`protected-route` で遷移元を保持、`login-page` で復帰） | 指定方式をそのまま成立させられる。Tauriのディープリンク復帰にも効く正攻法で、テスト専用deep-linkにも当たらない。ただし**認証フローのコード変更**であり、レビューが必要 |
| B   | ブラウザでviewerログイン後、SPA内ナビゲーションで編集ルートへ遷移して確認                           | コード変更不要。ただし「URLを直接入力する」の忠実な再現ではなく、指定の趣旨を満たすかの判断が必要                                                                      |
| C   | web buildのときだけ `persistSession: true` にする                                                   | Batch 5の設計判断（localStorageへセッションを置かない）に正面から反する。被検体が本番と異なるコード経路になるため**推奨しない**                                        |
| D   | S3-3のUAT要件を再定義し、一次証跡（RLS pgTAP + 上記route guardテスト）で充足とする                  | 実アカウント確認は行わない判断。Q2で「UAT証跡」を正式構成に含めた意図と衝突するため、判断を仰ぎたい                                                                    |

テスト専用deep-linkの実装が引き続き不許可であることは前提として維持している。

## 照会したいこと

1. **A〜Dのどれを採るか。** 実装者としてはAが筋が良いと考えるが、production適用直前に認証フローへ手を入れる是非の判断を仰ぎたい（Aを採る場合、適用後に回すことも可能）
2. Aを採る場合、**復帰先の受け渡し方式**（`Navigate` の `state` か、`?redirect=` クエリか）と、オープンリダイレクト防止（同一オリジン・既知ルートのみ許可）の要求水準
3. Bを採る場合、**S3-3の合格条件の書き換え文言**（「URLバーからの直接入力」を「SPA内遷移で編集ルートへ到達し、閲覧専用パネルを確認」へ変更してよいか）
4. UAT対象ルートを6とするか、`/candidates/import` を含めた7とするか

## 補足

本件はproduction適用（未適用migration 7本 + Batch 6A）とは独立している。適用作業自体はWSL2/Dockerが使える作業機へ移して継続中で、S3-3はStage 3Aの項目として残っている。
