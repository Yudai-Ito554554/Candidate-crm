# Fable 5決定: S3-3(viewer直URLアクセス)の検証方式 再決定

- 日付: 2026-08-19
- 前回決定: Batch 1レビュー(2026-08-12)論点G — 「staging web buildをブラウザで起動し、viewerでURLバーから編集ルートを直打ちする」
- 本文書: 上記を**撤回**し、新方式を決定する
- 照会元: `docs/fable5-request-s3-3-viewer-direct-url-2026-08-19.md`

## 1. 前提が崩れた理由(照会内容の追認)

報告は正確で、コード上の根拠も妥当である。

前回方式は「Tauriでもブラウザでも同一のReact SPA」という前提に立っていた。UIとルーティングでは今も成立するが、**セッション永続化層では成立しない**。`persistSession: false` かつ復元経路が `isTauriRuntime()` 分岐のOS資格情報ストアのみであるため、ブラウザでは常に未ログインで着地する。localStorageフォールバックはBatch 5で明示的に禁止した。

重要なのは、**この前提はQ2回答時点(2026-08-12)では成立していた**ことである。崩したのは翌日承認したBatch 5(2026-08-13)であり、そのレビュー時に私はS3-3への波及を検討しなかった。設計変更が既存の検証方式を無効化する連鎖を見落としたのは私の側の欠落である。

## 2. 決定: **D(UAT要件の再定義)**。A・B・Cは採らない

### 2.1 却下理由

- **A(ログイン後の要求ルート復帰)**: 機能としては妥当だが、**チェックリスト項目を満たすために本番コードを変更する**構図になる。「本番コードへテスト専用の導線を追加しない」というBatch 1で確立した原則の精神に反する。deep link復帰のUX改善として独立に実装する分にはよく、その場合は別項目として起票すること。S3-3の合格条件にはしない。
- **B(SPA内遷移)**: 「URLを直接入力する」の再現になっていない。ただし後述のとおり、**再定義後の要件では中核**になる。
- **C(web buildのみ `persistSession: true`)**: Batch 5設計に正面から反する。環境差でセッション永続の可否が変わる構成は、将来「ブラウザでも動かしたい」という要求が出たときに平文永続が静かに復活する経路を作る。不許可。

### 2.2 再定義の根拠

S3-3が守ろうとしているのは「viewerが編集画面へ到達し、編集操作ができてしまう」ことである。現在の配布物はTauriデスクトップアプリで、**URLバーが存在しない**。したがって「URLを直接入力する」という操作は、出荷される製品において実行経路が存在しない。存在しない操作を実機で再現しようとして本番コードを変えるのは本末転倒である。

加えて、権限の正本はRLSであり、仮にUIを突破されても書き込みはDBで拒否される(pgTAPで固定済み)。UI側の遮断は多層防御の一層にすぎない。

## 3. S3-3の新しい合格条件

次の3点すべてを満たすことをもって合格とする。

**(1) 一次証跡: 自動テスト**

`src/pages/app-routes.test.tsx` が、全編集ルートについて `editor-route.tsx` の閲覧専用パネル(`role="alert"` の「閲覧専用アカウントです」)を assert していること。これがルーティング層の遮断の正本。

**(2) 権限境界の証跡: pgTAP**

viewerが業務テーブルへINSERT/UPDATEできないことがpgTAPで固定されていること。**`supabase/tests/007_viewer_write_denial.test.sql` により2026-08-19に新規に固定した。**

> **訂正(2026-08-19、Fable 5)**: 起案時は「既に達成済み」と記載したが、これは未確認の推測だった。既存pgTAPは51個のpolicy式が `current_profile_role()` を参照することを構造として確認していたのみで、実際の書き込みを試みる検証のfixtureは admin / suspended / pending の3ロールに限られ、viewerロールでINSERT/UPDATEを試みる検証は存在しなかった。

**(3) 実機UAT: Tauriアプリ内での到達試行**

staging Tauriアプリにviewerでログインし、**アプリ内で到達可能なあらゆる経路から編集画面への到達を試み、いずれも閲覧専用パネルが出るか導線自体が存在しないことを確認する**。具体的には:

- グローバル作成メニュー(新規候補者・企業・求人)に導線が出ないこと
- 候補者・企業・求人の各詳細画面に編集ボタンが出ないこと
- 候補者取り込み画面(`/candidates/import`)への導線が出ないこと
- 一覧・詳細・タブ切替を一通り操作し、編集フォームへ到達できないこと

**合格の観測は「ログイン画面が出ること」ではなく「閲覧専用パネルの表示、または導線の不在」**である。照会文書の指摘どおり、`editor-route.tsx` はリダイレクトせずパネルを出す実装なので、ここを取り違えると誤判定になる。

### 3.1 任意(実施できるなら望ましい)

staging QAビルドで開発者ツールが開ける場合、コンソールから `history.pushState` 等でルートを直接切り替え、パネルが出ることを確認する。これは「URL直打ち」に最も近い再現であり、本番コードの変更を伴わない。開けない場合は不要 — (1)〜(3)で合格とする。

## 4. 6ルート/7ルートの不一致について

**チェックリストを7ルートへ修正すること。** 自動テストが `/candidates/import` を含めて7ルートを対象にしているのが正しい。取り込み画面は候補者を新規作成する経路であり、編集権限を要する。チェックリストの「6ルート」はこの画面が実装される前の記述が残ったものと判断する。
