# Candidate CRM ロールバック手順

この手順は、QA版または正式版の配布後に重大な不具合、権限逸脱、データ不整合が見つかった場合に使用します。候補者データを保護するため、デスクトップアプリ、Edge Function、データベースを別々の変更単位として扱います。

## 1. ロールバック開始条件

次のいずれかを確認した場合は、新規配布と利用拡大を停止します。

- 未承認ユーザーまたはviewerが業務データを変更できる
- 別ユーザーの認証状態、ファイル、候補者情報が表示される
- 登録・編集・アーカイブ・復元でデータ欠損または関連不整合が発生する
- アプリ起動、ログイン、主要一覧の表示が複数利用者で継続的に失敗する
- AI処理へ許可していない個人情報が送信される

## 2. 最初の対応

1. 配布中のインストーラーとダウンロードリンクを停止する
2. 対象バージョン、OS、発生時刻、利用者ロール、操作手順を記録する
3. 候補者本文や認証トークンをチャット、Issue、ログへ貼らない
4. SupabaseのAuth、Postgres、Storage、Edge Functionログを時刻とrequest IDで確認する
5. 影響範囲が不明な場合は書き込み操作を停止し、参照だけに限定する

## 3. デスクトップアプリの戻し方

- 配布済み成果物の`sha256-manifest.json`で対象バージョンとハッシュを確認する
- 問題のない直前バージョンの署名済み成果物とハッシュを確認する
- macOSは旧版`.app`または`.dmg`、Windowsは旧版`.msi`またはNSIS `.exe`を再配布する
- 再インストール後にログイン、ログアウト、セッション復元、ホーム表示を確認する
- Supabase Authのセッションはアプリ独自StorageではなくSupabase SDKが管理するため、原則として候補者データの端末移行作業は行わない
- 旧版が新しいDB列を知らない場合でも動作できるか、非本番で確認してから配布する

## 4. Edge Functionの戻し方

- デスクトップへAPIキーやservice roleを移動して回避しない
- 問題のあるFunctionだけを停止または直前のレビュー済みソースで再デプロイする
- `OPENAI_API_KEY`などのSecret値は再デプロイ時も出力しない
- AI生成を停止しても、直前の確認済みAIサマリーはアーカイブせず残す
- 招待Functionを停止した場合も既存利用者のAuthユーザーやプロフィールを削除しない

## 5. データベースの戻し方

既に適用したmigrationファイルを編集、削除、同じversionで再適用しません。

- まずRLSまたはRPCだけで安全に遮断できるか検討する
- 修正は新しい順方向migrationとして追加する
- 列やテーブルの削除は、アプリ互換性とバックアップを確認するまで行わない
- データ修復が必要な場合は対象IDと件数を読み取りクエリで確定し、レビュー済みSQLを非本番で検証する
- 本番データをローカルfixtureやスクリーンショットへコピーしない
- Point-in-Time Recoveryやバックアップ復元が必要な場合は、対象時刻と失われる可能性がある更新範囲を責任者が承認してから実施する
- migration履歴だけを修正してDB本体との不一致を隠さない

## 6. 復旧確認

- admin、agent、viewerで認証とRLS境界を再確認する
- 候補者・企業・求人・選考・活動・タスク・ファイルの主要操作を架空データで確認する
- 監査ログに対象操作が残り、候補者本文や変更前後の値が複製されていないことを確認する
- macOS・Windows双方でUATチェックリストの重大項目を再実行する
- 復旧版のSHA-256、commit、migration一覧、Edge Function versionを記録する

## 7. 再発防止

- 原因、検出できなかった理由、影響範囲、復旧時間を個人情報なしで記録する
- 再現テストを追加し、型チェック、Lint、全テスト、Webビルド、Tauriビルドを通す
- DB変更ではclean databaseへの全migration適用とpgTAPを再実行する
- 同じ事故を防ぐ自動チェックをCIへ追加してから再配布する
