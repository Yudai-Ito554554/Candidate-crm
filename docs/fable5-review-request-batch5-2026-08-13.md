## 1. レビュー目的

Fable 5設計の案Aに従い、Supabase Authのrefresh tokenだけをmacOS Keychain / Windows Credential Managerへ保存するBatch 5を実装した。mainへマージする前に、設計適合性、セキュリティ境界、セッション復元・移行・削除の意味論を正式レビューしてほしい。

このブランチではproduction / stagingへの接続、データ変更、DB migration追加を行っていない。

## 2. 実装概要

### 2.1 Tauri / Rust

- `keyring 3.6.3`を追加。default featureを無効化し、`apple-native`と`windows-native`だけを有効化した。
- `secure_credential_set/get/delete`の3コマンドを追加した。
- account/keyは`supabase-refresh-token`だけを許可し、任意キーを拒否する。
- Tauri config identifierから次のserviceへ固定マッピングする。
  - production: `com.candidatecrm.desktop.production`
  - staging: `com.candidatecrm.desktop.staging`
- 未知のidentifierはfail-closedで拒否する。
- OS資格情報ストア操作は`spawn_blocking`で行い、プロセス内Mutexで直列化した。
- エラーは値を含まない固定分類文字列へ変換し、refresh tokenをログやエラーへ含めない。
- Tauri 2のAppManifestからコマンドpermissionを生成し、`main`ウィンドウのdefault capabilityだけに許可した。

### 2.2 React / Supabase Auth

- Supabase clientを`persistSession: false`, `autoRefreshToken: true`へ変更した。
- access token・user・sessionはauth-jsのメモリ内だけに保持し、refresh tokenだけをOS資格情報ストアへ保存する。
- 起動時はOS資格情報ストアからrefresh tokenを読み、公開API`refreshSession({ refresh_token })`でセッションを復元する。
- `onAuthStateChange` callbackでは非同期処理を直接awaitせず、Promise queueへ直列化して渡す。
- `SIGNED_IN` / `TOKEN_REFRESHED`で最新refresh tokenを保存し、`SIGNED_OUT`で削除する。
- 無効・失効tokenは削除する。一時的な通信障害（`AuthRetryableFetchError`、status 0、5xx）では削除しない。
- OS資格情報ストアを利用できない場合もlocalStorageへフォールバックせず、将来の復元だけをfail-closedにする。現在のメモリ内セッションは継続可能とした。

### 2.3 旧localStorageセッション移行

- 対象キーはSupabase標準の完全一致キー`sb-<project-ref>-auth-token`だけとした。
- JSONからrefresh tokenだけを取り出し、OS資格情報ストアへ移送する。
- 移行の成功・失敗にかかわらず旧平文キーを削除し、再実行可能にした。
- localStorage削除自体が失敗した場合、移行直後のOS資格情報も可能な限りロールバックし、平文とOS資格情報の二重保持を移行成功として扱わない。
- localStorageからパスワード、access token、user情報を移送・保存しない。

## 6. Fable 5へ確認してほしい論点

1. `persistSession: false` + 明示的`refreshSession` + auth event queueの構成は、設計案AとSupabase Authのイベント意味論に適合しているか。
2. `SIGNED_IN`時の明示保存とauth event経由の保存、`signOut`時の明示削除とauth event経由の削除が重複し得るが、操作は冪等で、ログインAPI完了前の確実な保存・ログアウトAPI完了前の確実な削除を優先した。この判断を許容するか。
3. forced terminationがtoken rotation直後の短い保存窓で起きた場合、次回に再ログインが必要になる可能性を許容し、平文fallbackを作らない判断でよいか。
4. localStorageの削除に失敗した場合、移送済みOS資格情報を削除してfail-closedに戻す処理は妥当か。
5. `keyring`の`apple-native` / `windows-native`限定featureと、Rust側の固定service・固定account・固定エラー分類は十分に狭い境界か。
6. Tauri command permissionが`main`ウィンドウだけに限定されていること、値のallowlistをRust側でも強制していることは十分か。
7. 現在のテストで欠けているBlocker / High / Medium相当の回帰シナリオがないか。
8. macOS実機UATをmainマージ前の条件とし、Windows実機UATはWindows端末入手後に行う条件でよいか。
