# Candidate CRM

転職エージェント向け候補者 CRM のデスクトップアプリです。macOS と Windows の双方で動作する候補者中心の業務UI、Supabase認証、データベース基盤、候補者・職歴・タグ管理を含みます。

## 技術スタック

- Tauri 2 / React / TypeScript / Vite
- Tailwind CSS / shadcn/ui
- React Router / TanStack Query
- React Hook Form / Zod
- Vitest / Testing Library
- ESLint / Prettier

## 必要環境

- Node.js 22 以上
- npm 10 以上
- Rust stable
- Tauri 2 の OS 別 prerequisites

Tauri の prerequisites は[公式ドキュメント](https://v2.tauri.app/start/prerequisites/)を参照してください。Windows では Microsoft C++ Build Tools と WebView2、macOS では Xcode Command Line Tools が必要です。

## セットアップ

```sh
npm install
```

`.env.example` を `.env` にコピーし、SupabaseのProject URLとPublishable keyを設定してください。不足または形式不正の場合は、CRM画面の代わりに設定エラー画面を表示します。

```sh
cp .env.example .env
```

`service_role`キーはデスクトップアプリへ設定しないでください。

## 開発

ブラウザでフロントエンドを起動します。

```sh
npm run dev
```

Tauri デスクトップアプリを起動します。

```sh
npm run tauri dev
```

## 品質チェック

```sh
npm run typecheck
npm run lint
npm test
npm run format:check
npm run build
npm run verify:repo
```

`verify:repo`はmacOS・Windows共通のNode.jsスクリプトで、`.env.example`、migration名と順序、秘密鍵らしき値、OS固有の絶対ユーザーパス、Tauriの本番CSPを検査します。GitHub Actionsでは両OS上でこれらの品質チェックと`cargo check`を実行します。

CIのDBジョブはUbuntu上のローカルSupabaseへ全migrationを先頭から適用し、pgTAPで外部キー、RLS、クライアント権限、サーバー専用テーブルを検証します。このジョブはリモートSupabaseへ接続せず、秘密情報も使用しません。

Tauri アプリ自体のビルドは次のコマンドです。

```sh
npm run tauri build
```

Tauriの本番WebViewにはCSPを設定しています。標準の`*.supabase.co`以外のSupabaseカスタムドメインを利用する場合は、リリース前に`src-tauri/tauri.conf.json`の`connect-src`をそのドメインへ限定して追加してください。開発時はViteの動的なローカル接続を妨げないよう`devCsp`を無効にしています。

macOS・Windowsの社内QA成果物は、GitHub Actionsの`Desktop QA artifacts`を手動実行して生成します。macOS QA版にはブラウザ経由の取得で壊れたアプリと判定されないようアドホック署名を付け、`.app`とDMG内の署名をアップロード前に検証します。これはAppleによる本人確認やNotarizationではありません。ビルドにはRepository secretsの`VITE_SUPABASE_URL`と`VITE_SUPABASE_PUBLISHABLE_KEY`が必要です。一般配布前の正式署名、Notarization、インストール確認は[`docs/release-checklist.md`](docs/release-checklist.md)に従ってください。

## Phase 3B のデータモデル

初期スキーマは次の業務データを分離して管理します。

- `profiles`: `auth.users`に対応するアプリ利用者
- `candidates` / `candidate_experiences`: 候補者と職歴
- `companies` / `company_contacts`: 採用企業と企業側担当者
- `jobs`: 求人
- `applications`: 候補者と求人の選考関係
- `activities`: 発生済みの連絡・面談・選考イベント
- `tasks`: 今後行う業務と期限・完了状態
- `files`: Storage上のファイルを参照するメタデータ
- `email_threads` / `email_messages`: Inboxの対応状態とメール本文
- `tags`: 医療領域、職種、地域、役職、語学などの検索分類
- `candidate_tags` / `company_tags` / `job_tags`: 各業務データとタグの関連

主な関係は `candidate -> applications <- job -> company` です。活動・タスク・ファイルは候補者、企業、求人、選考へ任意で関連付けられます。`application_id`を設定した場合は、関連する候補者・求人との不整合をDBトリガーで拒否します。`owner_id`はプロフィールではなく認証主体である`auth.users(id)`を直接参照し、`profiles`は表示名とロールを保持する1対1の付加情報として扱います。

候補者ステータスはエージェントとの関係全体、選考ステータスは候補者と特定求人の組み合わせを表します。同じ「選考中」というUI表示でも保存先と状態遷移は別です。

`activities`は過去に起きた事実の時系列記録、`tasks`は期限・優先度・完了状態を持つ将来の作業です。Zoom、Teams、対面面談は共通の`meeting`活動として記録できます。`activities.ai_generated`はメール、要約、議事録などがAI生成かを識別します。タスク種別はfollow-up、電話、メール、面談、提案、選考、社内作業の必須値です。

候補者の社内メモは、将来の候補者向け表示やAI共有データと混同しないよう`private_notes`に限定しています。企業には業種、従業員数、資本金、上場有無、Webサイトを保持し、将来の検索・AI分析に利用できる構造にしています。

タグはJSONへ埋め込まず正規化テーブルで管理します。同じ名称のactiveタグや、同じ対象へのactiveな重複付与は部分一意インデックスで防ぎます。タグ解除は関連行の`archived_at`更新で表現します。

### 再応募とactiveな重複選考

`applications`には `(candidate_id, job_id)` の単純な一意制約を付けません。終了状態（入社・辞退・見送り）またはアーカイブ済みの選考がある場合は、同じ求人への再応募を作成できます。一方、終了していない同一候補者・求人の重複は部分一意インデックスで防ぎます。

## RLSとアクセス方針

全21テーブルでRLSを有効化しています。初期版は単一組織を前提とし、承認済みの`authenticated`ユーザーだけが許可された業務データを参照・更新できます。public業務テーブルのDELETEポリシーは作成せず、権限も明示的に取り消しています。

新しいAuthユーザーのprofileは`pending`で作成され、自分のprofile以外のCRMデータを参照できません。管理者が`agent`または`viewer`へ変更すると利用可能になります。承認済みユーザーがprofileで更新できるのは自分の`display_name`だけです。roleやemailの直接変更は許可しません。anonはすべての業務テーブルへアクセスできません。

複数組織対応時は各業務テーブルへ`organization_id`を追加し、組織メンバーシップを基準にRLSを置き換えます。現在の「authenticatedなら全件」のポリシーをそのまま本番の複数組織環境へ流用しないでください。

## マイグレーション

初期マイグレーションは `supabase/migrations/20260806082242_initial_crm_schema.sql` です。リモートへ適用する前に、ローカルSupabaseでレビュー済みmigrationを検証します。

```sh
npm run supabase:check:local
npm run supabase:start
npm run supabase:reset
npm run supabase:test
npm run supabase:stop
```

非本番プロジェクトへ明示的にlinkした後の差分確認と適用例は次の通りです。

```sh
npx supabase login
npx supabase link --project-ref <NON_PRODUCTION_PROJECT_REF>
npm run supabase:check:linked
npx supabase db diff --linked
npx supabase db push --dry-run
npx supabase db push
```

`db push`は自動rollbackされません。適用前にバックアップ、SQLレビュー、対象project refを確認してください。詳細は `supabase/README.md`を参照してください。

`supabase login`はCodexの非対話コマンド実行欄ではなく、macOSのターミナルまたはWindows Terminalなど、入力プロンプトを表示できるローカルターミナルで実行します。Supabase Dashboardで発行した個人アクセストークンをCLIのプロンプトへ直接入力してください。アクセストークン、データベースパスワード、service role keyを`.env`、ソースコード、Issue、チャットへ貼り付けないでください。`VITE_SUPABASE_PUBLISHABLE_KEY`はデスクトップアプリ用の公開キーであり、CLIの管理操作には使用できません。作業終了後に共有端末から認証状態を消す場合は`npx supabase logout`を実行します。

ローカル検証前は`npm run supabase:check:local`、非本番プロジェクトへlinkした後は`npm run supabase:check:linked`を実行します。これらは秘密値を表示せず、URL・Publishable key、CLI、CLI認証、Docker、link状態、`.env`とproject refの不一致を検出します。

Supabase CLIは開発依存関係としてバージョンを固定しています。グローバルCLIは不要で、ローカル操作とCIは同じCLI版を使用します。

## TypeScript型

`src/types/database.ts`はPhase 3Bの手動アプリ型です。Row・Insert・UpdateとDB CHECK制約に対応するunionを定義しています。日本語UI型との変換は`src/types/database-status.ts`で明示しています。

`src/types/database.generated.ts`はCLI生成用の予約ファイルで、偽のgenerated型は手書きしていません。migration適用後は次のコマンドで生成します。

```sh
npx supabase gen types typescript --local > src/types/database.generated.ts
```

linked済みの非本番環境を使用する場合:

```sh
npx supabase gen types typescript --linked > src/types/database.generated.ts
```

## Phase 3C の候補者CRUD

候補者一覧と候補者詳細はTanStack Queryを通じてSupabaseの`candidates`を参照します。新規登録・編集・アーカイブを実装し、新規候補者の`owner_id`には現在の`auth.users.id`を設定します。物理DELETEは使用しません。

- `/candidates`: 検索・絞り込み付き実データ一覧
- `/candidates/new`: 候補者登録
- `/candidates/:candidateId`: 候補者詳細
- `/candidates/:candidateId/edit`: 編集・アーカイブ

フォームはReact Hook FormとZodで検証し、空の任意項目はDB向けに`null`へ正規化します。保存成功後は候補者一覧・詳細のTanStack Queryキャッシュを更新します。取得・保存エラーは候補者情報やDB内部メッセージを露出しない日本語表示に変換します。

候補者画面内のAI表示はPhase 3X以降、サーバー生成データへ移行しています。

## Phase 4B の候補者パイプライン

候補者一覧内と`/pipeline`のパイプラインは、Supabaseの候補者・プロフィール・選考データを表示します。admin・agentがカードを別の列へドラッグするか、カード内のステージ選択を変更すると`candidates.candidate_status`を更新し、候補者一覧・詳細と同じTanStack Queryキャッシュへ反映します。保存失敗時は楽観的更新を取り消して元の列へ戻します。viewerは変更操作を利用できません。

パイプラインの列は業務上の大分類です。同じ列に含まれる細かな候補者ステータスは、別の列へ移動した時点でその列の標準ステータスへ更新されます。選考の一次面接・二次面接などは`applications.application_status`で管理し、候補者パイプラインを細分化しません。

## Phase 4C のロール権限強化

`set_profile_role`はプロフィールが欠損してロールを判定できない場合も管理者権限なしとして拒否します。管理者変更はトランザクション単位で直列化し、複数管理者が同時に自身を降格して管理者が0人になる競合を防ぎます。この修正は既存migrationを書き換えず、`20260806082431_profile_role_security_hardening.sql`で順方向に適用します。

## Phase 3D の職歴・タグ管理

候補者詳細の「職務経歴」タブはSupabaseの`candidate_experiences`を参照し、職歴の追加・編集・アーカイブに対応します。React Hook FormとZodで勤務先必須、在籍期間の前後関係を検証し、在籍中の職歴には終了日を保存しません。アーカイブ済み職歴は一覧から除外し、物理DELETEは使用しません。

「概要」タブでは正規化済みの`tags`と`candidate_tags`を利用し、既存タグの付与、新しい共通タグの作成・付与、タグ解除を行えます。同名の既存タグがある場合は再作成せず既存タグを付与します。タグ解除も関連行の`archived_at`更新で表現します。各操作後は候補者単位のTanStack Queryキャッシュを再取得します。

## Phase 3E の求人提案・選考管理

候補者詳細の「求人・選考」タブ、求人一覧、求人詳細はSupabaseの`applications`、`jobs`、`companies`、`company_contacts`を参照します。候補者から求人を提案し、選考ステータス、提案・応募日時、次回予定、辞退・見送り理由、社内メモを追加・更新できます。選考を一覧から除外する操作は`archived_at`を更新し、物理DELETEは使用しません。

同じ候補者・求人の進行中選考はDBの部分一意インデックスとUIの求人選択肢の双方で重複を防ぎます。入社・辞退・見送りで終了した選考がある場合は再応募を登録できます。求人一覧の選考中人数と求人詳細の候補者・選考表示も同じ選考データから算出します。求人・企業自体の登録・編集フォームは次Phase以降の範囲です。

## Phase 3F の企業・求人管理

求人一覧から企業管理へ移動でき、企業の追加・編集・アーカイブと、企業ごとの採用担当者の追加・編集・アーカイブを行えます。企業には業種、所在地、従業員数、資本金、上場区分、Webサイト、社内メモを保存します。採用担当者は求人の担当者として選択できます。

求人は追加・編集・アーカイブに対応し、企業、同一企業に所属する採用担当者、職種、勤務地、年収、募集期間、要件、社内メモを管理します。新規求人の`owner_id`には現在の`auth.users.id`を設定します。求人で使用中の企業・担当者や、選考が紐付く求人はアーカイブできません。この参照整合性はUIだけでなくDBトリガーでも検証します。

## Phase 3G の活動・タスク管理

候補者詳細の「タイムライン」はSupabaseの`activities`を参照し、活動の追加・編集・アーカイブに対応します。メール、面談、電話、求人提案、応募、選考結果、メモなどを日時順にまとめ、求人・選考・担当者との関連も表示します。手動登録した活動は`ai_generated = false`として保存します。

候補者詳細の「タスク」と全体の「タスク」、および「今日の予定」はSupabaseの`tasks`と`activities`を共通の取得基盤から表示します。タスクは追加・編集・完了・再開・アーカイブが可能で、候補者、求人、選考、期限、優先度、待ち状態を管理します。完了は`completed_at`、一覧から除外する操作は`archived_at`で表現し、物理DELETEは使用しません。

## Phase 3H のファイル管理

候補者詳細の「ファイル」と求人詳細の「ファイル・求人票」は、Supabase Storageの非公開`crm-files`バケットと`files`メタデータを利用します。PDF、Word、JPEG、PNGを10MBまでアップロード・ダウンロードでき、履歴書、職務経歴書、求人票、応募書類、資格・証明書、その他に分類します。

Storageパスには元のファイル名を含めず、`auth.users.id / 対象種別 / 対象ID / UUID`で構成します。ファイル名は認証済みユーザーだけが参照できる`files`テーブルに保存します。通常操作ではStorageオブジェクトを削除せず、メタデータの`archived_at`で一覧から除外します。StorageのDELETEポリシーは、メタデータ作成失敗時にアップロードした本人のフォルダだけを補償削除するために限定しています。

## Phase 3I のInbox基盤

InboxはSupabaseの`email_threads`と`email_messages`を参照します。スレッドには候補者、企業、求人、選考、プロバイダー、対応状態、AI下書き有無を関連付け、メール本文は送受信方向、送信者、宛先、送信日時、添付有無、AI生成有無を持つ独立したメッセージとして保存します。

デスクトップクライアントはメールスレッドと本文を参照し、スレッドの「未対応・返信待ち・対応済み」だけを変更できます。同期データのINSERTやメール本文のUPDATE・DELETE権限は付与していません。Gmail・Outlookからの取り込みは、クライアントへ秘密鍵を置かないサーバー側同期として次Phase以降に実装します。

## Phase 3J のホーム集約

ホームはSupabaseの候補者、選考、求人、企業、活動、タスク、InboxをTanStack Queryで取得し、今日の予定、期限超過、待ち状態、最近の活動、補助KPIへ集約します。今日が期限のタスクと当日の面談・電話予定を同じ一覧に表示し、タスクはホームから完了できます。

閲覧履歴を端末へ保存しない方針のため、候補者欄はレコードの`updated_at`に基づく「最近更新された候補者」です。正確な閲覧履歴が必要になった場合は、ユーザーと候補者を関連付ける監査可能なDBテーブルを設計します。

## Phase 3K のレポート集約

レポートはSupabaseの候補者、選考、活動から、選択月の新規候補者、面談・電話、求人提案、応募、書類通過、面接、内定、入社を集計します。候補者ステージは現在の`candidate_status`、月次ファネルは選考日時と活動日時を利用し、外部チャートライブラリを使わず数値・棒表示・テーブルで表現します。

## Phase 3L の選考ステータス履歴

`application_status_history`は選考作成時の初期状態と、その後のステータス変更をDBトリガーで記録します。既存選考はmigration適用時に現在状態を`is_backfilled = true`の初回履歴として補完します。変更者は`auth.uid()`を記録し、デスクトップクライアントにはSELECTだけを許可します。

レポートの書類通過と内定はこの履歴を基準に集計し、バックフィル行は実績から除外します。履歴導入前の過去の中間遷移は復元できないため、導入後に記録された遷移だけが正式な実績になります。

## Phase 3M の選考履歴UI

候補者詳細の「求人・選考」タブでは、候補者に関連する選考ステータス履歴を最新20件まで表示します。変更日時、企業・求人、遷移前後のステータス、変更者を確認でき、migrationで補完された行は「移行時点の状態」と明示します。履歴は参照専用で、画面からの編集・削除はできません。

## Phase 3N の候補者閲覧履歴

候補者詳細を開くと、限定RPCの`record_candidate_view`が`auth.uid()`と候補者の組み合わせをupsertし、最新の`viewed_at`を記録します。ホームの「最近見た候補者」はこの履歴を表示します。閲覧履歴はユーザーごとにRLSで分離し、候補者情報や閲覧履歴をlocalStorageへ保存しません。デスクトップクライアントには`candidate_views`のINSERT・UPDATE・DELETE権限を付与しません。

## Phase 3O の企業・求人タグ

企業編集画面と求人詳細の概要タブでは、共通の`tags`と正規化済みの`company_tags`・`job_tags`を利用してタグを管理します。既存タグの付与、新しい共通タグの作成・付与、関連行のアーカイブによる解除に対応します。候補者・企業・求人でタグ本体を共有し、分類をJSONへ重複保存しません。

## Phase 3P の求人活動履歴

求人詳細の「活動履歴」タブは、候補者タイムラインと共通のSupabase `activities`を`job_id`で絞り込み、最新30件を日時順に表示します。活動種別、本文、関連候補者、担当者、AI生成区分を一画面で確認でき、関連候補者から候補者詳細へ移動できます。履歴は参照専用で、編集・アーカイブは候補者タイムラインから行います。

## Phase 3Q の企業詳細

企業一覧から企業詳細へ移動し、企業情報、取引状況、正規化タグ、採用担当者、求人・選考、社内メモをタブで確認できます。「活動履歴」タブは共通のSupabase `activities`を`company_id`で絞り込み、関連候補者、求人、担当者、AI生成区分を含む最新30件を表示します。企業・求人・活動を複製せず、既存テーブル間の関連から企業単位の業務ビューを構成します。

## Phase 3R の企業ファイル管理

企業詳細の「ファイル」タブは、候補者・求人と共通の非公開Supabase Storageと`files`メタデータを利用します。企業資料、契約書などをPDF、Word、JPEG、PNGで10MBまでアップロード・ダウンロードでき、一覧から除外する操作は`archived_at`によるアーカイブです。Storageパスは`auth.users.id / companies / company_id / UUID`で構成し、元のファイル名をパスへ含めません。

企業ファイル一覧の取得性能を保つため、`20260806082306_company_files_index.sql`でactiveな`company_id, created_at desc`の部分インデックスを追加します。

## Phase 3S のプロフィール・ロール管理

設定画面では、ログインユーザーが自分の表示名を変更し、チーム利用者の表示名、メールアドレス、ロールを確認できます。`admin`は限定RPC `set_profile_role`を通じて利用者を承認待ち・管理者・エージェント・閲覧者へ変更できます。最後の管理者が自分を降格する操作はDBで拒否します。クライアントへ`profiles.role`の直接更新権限は付与しません。

`20260806082308_profile_role_permissions.sql`では、業務データの追加・変更・アーカイブとStorageアップロードを`admin`・`agent`に限定します。`viewer`は候補者、企業、求人、活動などを参照できますが、RLSにより業務データを書き込めません。画面側の表示制御だけを権限境界として扱わず、Supabase側で必ず拒否します。

初回adminはmigration適用後、Supabaseプロジェクト管理者が対象ユーザーを確認して非本番環境で明示的に設定してください。以後の利用者は設定画面からadminが招待し、agentまたはviewerのロールを付与できます。招待処理は認証済みJWTとadminロールを検証するEdge Functionで行い、秘密鍵をデスクトップへ置きません。

`20260806082433_pending_access_and_email_sync_hardening.sql`以降、新規ユーザーは管理者承認までCRM画面を開けません。同migrationは過去メールの初回同期でもInboxの最終送信者・プレビュー・日時を更新します。ホームとレポートで使う主要一覧は、PostgRESTの最大行数で欠落しないようページング取得します。

## Phase 3T の閲覧専用UI

ログインユーザーの`profiles.role`を共通アクセスフックで確認し、`viewer`には全画面で閲覧専用バナーを表示します。候補者・企業・求人の新規登録／編集ルートは共通ガードで保護し、URLを直接開いてもフォームを描画しません。

候補者の活動・職歴・求人提案・タスク・タグ、全体タスク、今日の予定、ホーム、Inbox、ファイル管理、企業・求人タグなどの主要な変更操作も閲覧者には表示しません。候補者パイプラインは閲覧できますが、ドラッグ＆ドロップによる状態変更は無効です。UI制御は操作ミスを防ぐためのものであり、最終的な権限判定はPhase 3SのSupabase RLSが行います。

## Phase 3U のAI Summary基盤

候補者詳細の「AI」タブはSupabase `ai_summaries`から最新の生成結果を参照します。候補者サマリー、転職理由、強み、懸念点、面談確認事項、推奨求人、次回アクションを分離し、生成モデル、プロンプトバージョン、参照活動の期限、生成日時も表示します。メール下書きはAIサマリーの対象に含めません。

AI本文のINSERT・書き換え・削除はデスクトップクライアントへ許可しません。将来のEdge Functionがサーバー側で生成・保存し、admin・agentは内容を確認した事実だけを`reviewed_by`・`reviewed_at`へ記録できます。`viewer`は生成結果を参照できますが確認状態を変更できません。AI出力は候補者への送信や求人提案前に人間が確認する補助情報として扱います。

## Phase 3V の横断検索

ヘッダーの全体検索から、候補者・企業・求人・それぞれに紐付く正規化タグを横断して検索し、詳細画面へ直接移動できます。日本語の氏名、企業名、職種、勤務地などを部分一致で探せるよう、PostgreSQLの`pg_trgm`索引を利用します。入力は250ms待ってから検索し、2文字未満ではRPCを呼び出しません。

検索RPCは`security invoker`として実行し、候補者・企業・求人テーブルの既存RLSをそのまま適用します。`anon`には実行権限を付与せず、検索結果や検索履歴をlocalStorageへ保存しません。1回の結果件数は最大30件、画面の既定値は12件です。

## Phase 3W の監査ログ

候補者、職歴、企業、企業担当者、求人、選考、活動、タスク、ファイル、メールスレッド、タグ関連、プロフィール、AIサマリーの作成・更新をDBトリガーで`audit_logs`へ記録します。アーカイブ、復元、タスク完了・再開、AI確認、ロール変更は通常更新と分けて記録します。

監査ログには実行者、操作、対象種別、対象ID、変更されたフィールド名、トランザクションID、日時だけを保存します。候補者情報、社内メモ、メール本文、AI出力、変更前後の値は複製しません。デスクトップクライアントからの追加・更新・削除は許可せず、設定画面では管理者だけが最新100件を閲覧できます。

## Phase 3X のAIサマリー生成

候補者詳細のAIタブから、admin・agentが確認ダイアログを経てSupabase Edge Function `generate-candidate-summary`を実行できます。Edge FunctionはログインJWTとプロフィールロールを確認し、同一候補者の同時生成と5分以内の連続生成を拒否します。viewerは生成ボタンを利用できません。

OpenAI Responses APIのStructured Outputsを利用し、モデルはコストを抑えるため`gpt-5.6-luna`を使用します。候補者の氏名、メール、電話、生年月日、`private_notes`はAI入力へ含めず、活動などの自由記述に含まれる候補者名・メール・電話も置換します。APIリクエストでは`store: false`を設定し、JSON Schemaに一致する日本語の業務補助情報だけを受け取ります。

生成結果のINSERTと旧サマリーのアーカイブは、service roleだけが実行できる`store_candidate_ai_summary`関数内で一括処理します。失敗時は直前の利用可能なサマリーを残し、生成要求には候補者本文やプロンプトを保存せず、状態と一般化したエラーコードだけを記録します。

デプロイ前に対象を非本番プロジェクトとして確認し、Secretを設定します。`OPENAI_API_KEY`やservice roleを`.env`、Vite、Tauriへ設定しないでください。

```sh
npx supabase secrets set OPENAI_API_KEY=<OPENAI_API_KEY>
npx supabase functions deploy generate-candidate-summary
```

## Phase 3Y の障害耐性

Reactルートの外側にアプリ全体のError Boundaryを配置し、認証ProviderやRouterを含む予期しない描画例外でも白画面にならないようにしています。画面単位の遅延ロードやloaderエラーはReact Routerのエラー画面で処理し、再読み込みとホームへの復帰導線を表示します。内部例外の本文、候補者情報、認証情報は画面へ表示しません。

存在しない認証済みURLは共通レイアウト内の404画面へ遷移します。ネットワーク切断時は全画面共通のオフライン通知を表示し、表示内容が古い可能性と、変更操作を接続回復後に行う必要があることを案内します。実装はブラウザ標準APIだけを使用し、macOS・Windows固有処理を追加していません。

## Phase 3Z の共通タグ管理

設定画面で候補者・企業・求人が共有するタグの作成と名称変更を行えます。admin・agentだけが編集でき、viewerには操作を表示しません。名称は前後の空白を除去し、1〜40文字に制限します。同名のactiveタグはデータベースの部分一意インデックスで拒否します。

タグ本体は物理削除せず、未使用の場合だけ`archive_unused_tag` RPCでアーカイブします。候補者・企業・求人のいずれかにactiveな関連が残るタグはデータベース側で拒否されるため、誤操作で既存分類が消えることはありません。アーカイブ操作は画面内の二段階確認を必要とします。

## Phase 4F の次回対応完了

候補者詳細の「次にやること」は画面内の確認を経て完了できます。`complete_candidate_next_action` RPCが候補者の次回対応・期限・待ち状態をクリアし、完了前の対応内容と期限を活動履歴へ同一トランザクションで保存します。途中失敗で候補者情報だけが消える状態を防ぎます。

完了操作はadmin・agentだけが実行でき、viewerはUIとデータベースの両方で拒否されます。成功後は候補者詳細、候補者一覧、タイムライン、ホーム用の活動キャッシュを更新します。

## Phase 4G のユーザー招待

設定画面からadminがメールアドレス、表示名、ロール（agentまたはviewer）を指定して利用者を招待できます。招待メールの送信とプロフィール権限の設定はSupabase Edge Function `invite-user`で行い、クライアントへ秘密鍵を渡しません。ユーザーメタデータは認可には使用せず、DBの`profiles.role`を権限の正本とします。

招待リンクは`candidate-crm://auth/callback`でTauriアプリを開きます。アプリは招待セッションだけを受け取り、初回パスワード設定画面へ遷移します。macOS・Windowsで二重起動を避けるためsingle-instanceプラグインを先に登録しています。Supabase Dashboardの **Authentication → URL Configuration → Redirect URLs** に次を追加してから招待を送信してください。

```text
candidate-crm://auth/callback
```

## Phase 4H のパスワード再設定

ログイン画面の「パスワードを忘れた場合」から再設定メールを送信できます。画面にはメールアドレスの登録有無を区別しない共通メッセージを表示し、アカウントの存在確認に悪用されにくい構成にしています。

再設定メールのリンクは招待と同じ`candidate-crm://auth/callback`でTauriアプリへ戻り、`type=recovery`のセッションだけをパスワード変更画面へ案内します。変更はSupabase Authの`updateUser`で行い、パスワードやトークンをアプリ独自のStorageへ保存しません。

## Phase 4I の共通新規登録メニュー

ヘッダーの「新規登録」から候補者、企業、求人の登録画面を選択できます。admin・agentだけに表示し、viewerには既存の共通アクセス制御により表示しません。メニュー外のクリックとEscapeキーで閉じられ、macOS・Windowsで共通のReact実装だけを使用します。

## Phase 4J の候補者からの求人提案導線

候補者詳細上部の「求人提案」から「求人・選考」タブへ移動し、その候補者を設定済みの提案フォームを直ちに開けます。提案可能な求人だけを選択肢に表示し、進行中の同一求人を重複登録できない既存制御を維持します。保存先は共通の`applications`で、ログインユーザーをownerとして記録します。

## Phase 4K の求人からの候補者提案導線

求人詳細上部の「候補者を提案」から候補者タブへ移動し、その求人を固定した提案フォームを開けます。候補者、初期ステータス、提案日時、次回予定、社内メモを入力し、共通の`applications`へ保存します。進行中の同一候補者・求人は選択肢から除外し、終了済み選考がある候補者の再提案は許可します。

## Phase 4L の未接続メール操作整理

メール下書き機能は採用しない方針に合わせ、候補者詳細の「メール作成」とInboxの「返信を作成」「AI下書き」を画面から撤去しました。メール連携がない状態で空振りする操作を表示せず、Inboxでは受信内容の確認、返信待ち、対応済みの業務ステータス管理だけを提供します。

## Phase 4M の候補者重複警告

新規候補者登録時に、RLSで参照可能な既存候補者と氏名、メールアドレス、電話番号を比較します。氏名は全半角と空白、メールは大文字小文字、電話番号はハイフンなどの表記差を正規化し、一致候補と一致項目を保存前に表示します。

同姓同名や共有連絡先を誤って拒否しないようDBの一意制約にはせず、担当者が既存候補者を確認した上で明示的に登録を続行できる警告型です。重複確認に必要な情報はlocalStorageや外部サービスへ保存しません。

## Phase 4N の企業重複警告

新規企業登録時に、RLSで参照可能な既存企業と企業名、Webサイトを比較します。企業名は全半角と空白、Webサイトはプロトコル、`www`、末尾スラッシュの表記差を正規化し、一致した企業と一致項目を保存前に表示します。

同名の別法人やグループ会社を登録できるようDBの一意制約にはせず、既存企業を確認した上で明示的に登録を続行できます。重複確認データはブラウザストレージや外部サービスへ保存しません。

## Phase 4O の求人重複警告

新規求人登録時に、RLSで参照可能な既存求人から同じ企業・求人名の組み合わせを検索します。求人名、事業部、職種は全半角と空白、勤務地は順序や区切り文字の表記差を正規化し、一致項目を保存前に表示します。

再募集や同名の別ポジションを登録できるようDBの一意制約にはせず、既存求人を確認した上で明示的に登録を続行できます。重複確認データはブラウザストレージや外部サービスへ保存しません。

## Phase 4P の候補者アーカイブ復元

候補者画面に「アーカイブ済み」表示を追加しました。通常一覧とは別のクエリで`archived_at`が設定された候補者だけを取得し、氏名、現勤務先・職種、居住地、ステータス、アーカイブ日時を確認できます。

admin・agentは候補者を通常一覧へ復元できます。復元は`archived_at`を`null`へ戻す論理復元で、物理DELETEや別ストレージへの複製は行いません。復元操作も既存の監査ログに`restore`として記録されます。

## Phase 4Q の企業・求人アーカイブ復元

企業管理と求人一覧にも「アーカイブ済み」表示を追加しました。通常データとは分離して取得し、企業は業種・所在地・Webサイト、求人は企業名・職種・勤務地・募集状況とアーカイブ日時を確認できます。求人では親企業がアーカイブ済みの場合も企業名を解決します。

admin・agentは企業・求人を通常一覧へ復元できます。候補者と同様に`archived_at`を`null`へ戻す論理復元で、物理DELETEは行わず、既存の監査ログへ`restore`として記録されます。

求人の親企業がアーカイブ済みの場合、UIは企業の復元を先に案内します。DBでも求人復元用トリガーが親企業と採用担当者のactive状態を検証し、クライアントを迂回した不整合な復元を拒否します。

## Phase 4R の未保存変更保護

候補者、企業、求人の登録・編集画面では、入力後に戻るリンク、サイドバー、キャンセルなどで画面を離れようとすると確認ダイアログを表示します。「編集を続ける」で入力内容を維持し、「保存せず移動」で明示的に破棄できます。ウィンドウを閉じる操作にも標準の離脱警告を設定します。

保存成功または確認済みのアーカイブ後の遷移はブロックしません。保存失敗時は入力画面に留まり、再編集・再送信できます。

## Phase 4S の求人票AI取り込み

新規求人登録では、求人票テキストの貼り付け、5MB以内の文字入りPDF、ログイン不要の公開HTTPS求人ページから求人情報を抽出できます。認証済みadmin・agentだけがJWT必須のSupabase Edge Functionを実行でき、OpenAI Responses APIのStructured Outputsを`store: false`で使用します。PDFと取得したWeb本文は一時的に処理し、Storageやデータベースへ自動保存しません。

URL取得はHTTPS・標準ポートだけに限定し、localhost、プライベートIP、予約IP、社内向けホスト名を拒否します。DNS解決結果と最大3回のリダイレクト先を毎回検証し、HTML・テキストは1MB、PDFは5MB、取得時間は15秒に制限します。ログイン必須ページ、JavaScript実行後にだけ内容が出るページ、アクセスを拒否するサイトは取り込めません。

抽出結果は自動登録せず、担当者が読み取り結果を確認してから既存フォームへ反映します。企業は登録済み企業名と正規化した完全一致の場合だけ自動選択し、不一致時は企業の登録または手動選択を求めます。画像だけのPDFに対する精度保証、抽出結果の無確認登録は現在の対象外です。

同じ登録画面で同一のテキスト、PDF、URLを再度読み取る場合は、直前の抽出結果をメモリ上で再利用し、OpenAI APIを重複実行しません。キャッシュは画面を閉じると破棄され、localStorageやデータベースには保存しません。読み取り結果には抽出元、時刻、取得項目数を表示し、フォーム反映後も人による確認が必要なことを案内します。

AI利用は候補者サマリーと求人票読み取りを合算し、利用者ごとに同時1件、直近1時間20回、直近24時間50回までをサーバー側で制限します。判定と利用枠の確保はPostgres内で原子的に行うため、機能をまたいだ連打や複数ウィンドウからの同時実行でも上限を迂回できません。候補者サマリーの候補者単位5分クールダウンも維持します。利用履歴には利用者、処理種別、開始・完了時刻、成否だけを記録し、求人票本文、URL、ファイル名、AI入力、抽出結果は保存しません。停止した求人票読み取りは5分、候補者サマリー生成は15分後に失敗扱いとなり、利用者を永続的にブロックしません。

## Phase 4T のAI利用状況

設定画面の「AI利用状況」は管理者だけに表示し、候補者サマリーと求人票読み取りを合算した直近1時間・24時間の利用数、残り回数、成功・失敗・実行中、機能別・利用者別の件数を確認できます。集計はPostgres内で行い、専用Edge Functionが件数だけを返します。候補者ID、求人票本文、URL、AI入力、AI出力、個別リクエスト明細はデスクトップへ返しません。画面は1分ごとに再取得でき、手動更新にも対応します。

## Phase 4U のAI利用枠警告

AI利用状況では、利用者ごとの1時間・24時間上限に対して80%以上を「注意」、90%以上を「残りわずか」、100%以上を「上限到達」として文字と色の両方で表示します。ログイン中の管理者自身が閾値へ達した場合は画面上部に警告を表示し、利用枠が回復するまで必要な生成を優先する判断ができます。

警告は既存の件数集計だけからクライアントで判定し、新しい候補者情報、求人票本文、AI入力・出力、個別リクエスト明細を取得しません。利用制限そのものは引き続きPostgres側の原子的な判定を正本とします。

## Phase 4V のAI実行前チェック

候補者AIサマリーと求人票AI読み取りでは、本人の直近1時間・24時間の利用件数を実行前に確認し、いずれかの上限へ到達している場合は生成ボタンを無効化します。生成成功後は利用件数を再取得するため、複数画面で同じ残り枠を共有できます。件数取得に失敗した場合は画面だけで永久停止せず、Postgres側の原子的な利用制限を最終判定とします。

`get-ai-usage` Edge Functionはadminにはチーム集計を返しますが、agentには本人の件数だけを返します。viewerはAI生成を実行できず、同Functionも利用できません。agentへ他利用者の件数、候補者ID、求人票本文、AI入力・出力、個別リクエスト明細は返しません。

## Phase 4W の本人向けAI残り枠表示

候補者AIサマリーと求人票AI読み取りには、本人の「直近1時間」と「直近24時間」の残り回数を共通表示します。通常・注意・残りわずか・上限到達を文字でも示し、上限に達する前に必要な生成を優先できます。利用履歴がまだない利用者には上限全数を残り回数として表示します。

表示にはPhase 4Vで本人へ限定した件数集計だけを使用します。候補者情報、求人票本文、AI入力・出力、他利用者の件数は取得せず、生成可否の最終判定は引き続きPostgres側で行います。

## Phase 4X のAI利用再開見込み

AI利用上限へ到達した場合は、ローリング1時間・24時間の各対象リクエストのうち最古の時刻から、再び生成可能になる見込み時刻を表示します。両方の上限へ到達している場合は、両条件を満たす遅い方の回復時刻を採用します。

回復時刻はPostgres内で件数と同時に集計し、日時だけを既存Edge Function経由で本人へ返します。個別リクエスト、候補者ID、求人票本文、URL、AI入力・出力は返しません。実行直前には引き続きDB側で現在時刻を使って上限を再判定します。

## Phase 4Y のAIトークン利用量

OpenAI Responses APIが返す入力・出力トークン数を、候補者サマリー生成と求人票読み取りの実行履歴へ記録します。管理者は設定画面で直近24時間のチーム合計・利用者別の入力トークンと出力トークンを確認できます。過去の実行やプロバイダーが利用量を返さなかった処理は0として集計します。

保存するのは非負のトークン数だけです。プロンプト、求人票本文、URL、ファイル名、候補者ID、AI出力は利用量テーブルや集計APIへ追加せず、金額換算もモデル価格の変更で誤解を生まないよう今回は行いません。

## Phase 4Z のAIモデル別利用量

候補者サマリーと求人票読み取りでは、OpenAI Responses APIが実際の応答で返したモデル識別子をトークン数と一緒に記録します。管理者は設定画面で直近24時間のモデル別実行回数、入力・出力・合計トークン数を確認でき、将来モデルを切り替えた際にも利用量を分離して比較できます。

モデル識別子は前後の空白を除いた1〜100文字だけを受け入れ、不正または欠落している場合はサーバー設定中のモデル名を使用します。記録開始前の履歴は「不明（記録開始前）」として集約し、プロンプトやAI出力は引き続き保存・返却しません。

## Phase 5A の求人票取り込み差分確認

求人票AI読み取り結果を入力欄へ反映する前に、項目ごとの現在値と反映後の値を一覧表示します。追加・変更・クリアを文字付きで区別し、担当者が変更内容を確認してから明示的に反映できます。

AIが取得できなかった項目はフォームパッチから除外し、担当者が先に入力した値を空文字で上書きしません。長文は差分表示だけを160文字で省略し、実際にフォームへ反映する値は省略しません。求人データの保存は引き続き通常の登録ボタンと既存の重複確認を通して行います。

## Phase 5B の求人票取り込み項目選択

求人票の差分確認では、反映する項目をチェックボックスで個別に選択できます。「すべて選択」「すべて解除」に対応し、反映ボタンには現在の選択件数を表示します。1項目も選択していない場合は反映できません。

選択されなかった項目はReact Hook Formへ書き込まず、既存の入力値を維持します。AI抽出結果そのものや選択状態はlocalStorageへ保存せず、画面を閉じると破棄します。

## Phase 5C の求人票取り込み上書き保護

求人票の差分確認では、未入力欄への「追加」だけを推奨項目として初期選択します。担当者が入力済みの値をAI結果で「変更」する項目と、関連値を「クリア」する項目は初期選択せず、内容を確認して明示的に選択した場合だけ反映します。

「推奨だけ選択」で安全な初期状態へ戻せるほか、必要な場合は「すべて選択」も利用できます。この判定は画面内の現在値と差分だけで行い、追加のAI API呼び出しやデータ保存は発生しません。

## Phase 5D の求人企業・採用担当者整合性保護

AI取り込みで求人の企業を変更する際、変更前の企業に属する採用担当者が残らないよう、企業変更と採用担当者のクリアを一組として選択します。企業変更を選ぶと必要なクリアも自動選択され、採用担当者のクリアを解除した場合は企業変更も解除されます。

画面にも連動する理由を表示し、求人と採用担当者の所属企業が食い違った状態をフォームから作らないようにしています。既存のデータベース検証も最終防御として維持します。

## Phase 5E の求人企業照合結果表示

求人票から読み取った企業名が登録済み企業と完全一致したかを、入力欄へ反映する前に表示します。一致した場合は反映対象の企業名を示し、一致しない場合や企業名を取得できなかった場合は企業欄を自動変更せず、手動選択が必要なことを明示します。

照合はRLSで参照できる企業名を画面内で正規化して比較する既存方式を維持し、類似名を推測で選択しません。照合表示のための外部通信やAI API呼び出しは追加しません。

## Phase 5F の求人登録必須項目確認

AI取り込みの差分と現在の選択内容を反映した仮のフォーム状態から、求人登録に必須の「企業」と「求人名」が揃うかを事前に表示します。不足している場合は項目名を明示し、企業未照合や項目選択解除によって、反映後に登録できない状態になることを確認できます。

判定はReactメモリ上の現在値と差分だけで行います。入力欄への反映やデータベース保存はせず、AI APIやSupabaseへの通信も追加しません。

## Phase 5G の求人条件矛盾チェック

AI取り込みで選択中の項目を現在のフォームへ反映した仮状態について、年収下限が年収上限を超える場合と、募集開始日が募集終了日を超える場合を事前に警告します。既存入力の片側だけをAI結果で更新して矛盾するケースも検出し、選択を変更すると警告も即時更新します。

警告は確認を促すもので、AI結果を自動修正したり推測値へ置き換えたりしません。実際の登録時には既存のZodフォーム検証も引き続き適用します。

## Phase 5H のAI注意事項確認

求人票読み取り結果にAIの注意事項が含まれる場合は、注意文の直下に確認チェックを表示します。担当者が「AIの注意事項を確認しました」を選択するまで入力欄へ反映できず、曖昧な年収、勤務地、募集条件などを読み飛ばしたまま登録作業へ進むことを防ぎます。

注意事項がない通常の結果には確認操作を追加しません。確認状態は画面内のReactメモリだけで保持し、元データを変更した場合や結果を再表示した場合は未確認へ戻します。

## Phase 5I の求人票読み取り競合防止

AI読み取りの実行中は、取り込み方式、テキスト、PDF、URLの入力を一時的に無効化し、処理開始後に入力元が変わって古い結果を誤って表示することを防ぎます。処理中であることは画面表示と読み上げ可能なステータスの両方で案内します。

各リクエストには画面内の識別番号を付け、入力変更などで結果が無効になった場合は、遅れて完了した応答をフォームへ表示しません。識別番号や読み取り結果は永続化しません。

## Phase 5J の求人票入力事前検証

貼り付けテキストには現在の文字数と30,000文字の上限、PDFにはファイル名と容量を表示します。テキストの長さ、PDFの形式・5MB上限、公開URLのHTTPS形式を入力時に検証し、不足や超過がある間はAI読み取りボタンを無効化します。

不正な入力をEdge Functionへ送信しないため、失敗が分かっているAI API実行と待ち時間を削減できます。サーバー側のサイズ、形式、URL安全性検証も迂回対策として維持します。

## Phase 5K のAI結果再利用表示

同じ求人登録画面で同一のテキスト、PDF、URLを再度読み取る場合は、既存の画面内キャッシュを利用したことと、追加のAI実行が発生していないことを読み取り結果へ表示します。担当者が再表示と再生成を区別でき、利用枠や料金への不安を減らします。

キャッシュは引き続きReactメモリ内だけに保持し、画面を閉じると破棄します。求人票本文、URL、PDF、AI結果をlocalStorageやデータベースへ保存しません。

## Phase 5L の複数求人票メモリキャッシュ

同じ求人登録画面で複数の求人票を行き来する場合に備え、直近3種類の読み取り結果を画面内キャッシュとして再利用します。別の求人票を確認した後で以前の内容へ戻っても、キャッシュ対象であればAI APIを再実行しません。

キャッシュ件数は3件に制限し、4件目を読み取る際は最も長く使われていない結果を破棄します。キャッシュには抽出結果と画面表示用の時刻だけを保持し、元のPDFファイルや本文を複製せず、画面を閉じるとすべて破棄します。

## Phase 5M の求人票セッション消去

「入力とキャッシュを消去」を選ぶと、貼り付けテキスト、公開URL、選択中PDF、読み取り結果、直近3件の画面内キャッシュを一括で破棄します。画面を閉じる前でも明示的に求人票データを消せるため、共有端末や画面共有後の運用にも対応できます。

消去後に同じ求人票を再度読み取る場合は新しいAI実行として扱います。Supabase上の登録済み求人や通常フォームへ既に反映した値は変更せず、AI取り込み領域の一時データだけを対象にします。

## Phase 5N の反映後確認フォーカス

AI読み取り結果を入力欄へ反映した直後は、選択した項目のうち最初に反映したフォーム項目へフォーカスを移します。長い求人登録画面でも確認開始位置が明確になり、キーボード利用者はそのままTabキーで反映内容を順番に確認できます。

フォーカス移動は既存のReact Hook Form機能を使用し、画面座標やOS固有APIには依存しません。反映対象がない場合は移動せず、macOSとWindowsで同じ項目順を維持します。

## Phase 5O の反映完了サマリー

AI読み取り結果を入力欄へ反映した後は、反映した項目数と、選択せず保留した項目数を完了案内へ表示します。あわせて求人の登録自体はまだ完了していないことを明示し、AI結果の反映とデータベースへの登録を取り違えないようにしています。

反映後は差分プレビューと選択状態を閉じ、同じ内容を誤って二重反映しにくくします。元データと直近の読み取りキャッシュは画面内に残るため、必要な場合はAI APIを再実行せず、もう一度差分を確認できます。

## Phase 5P の必須項目フォーカス

AI結果の反映後に「企業」または「求人名」が不足している場合は、通常の反映順よりも不足中の必須項目を優先してフォーカスします。特に求人票の企業名が登録済み企業へ完全一致しなかった場合、そのまま企業選択へ進めます。

企業と求人名が揃っている場合はPhase 5Nどおり最初の反映項目へフォーカスします。判定は反映後のReact Hook Formの値だけで行い、追加のAI APIやSupabase通信は発生しません。

## Phase 5Q の求人票取り込みUAT資料

実在データを使わずテキスト貼り付けとPDFアップロードを確認できるよう、同じ架空求人を記載したテキストとPDFのテスト資料を用意しています。企業名には架空企業であることを明記し、非本番環境の業務受け入れテストだけで使用します。

`docs/uat-checklist.md`には、3種類の入力元、事前検証、差分選択、未登録企業、注意事項、キャッシュ、セッション消去、登録前状態までの確認手順を追加しています。テキストとPDFは同じ架空求人の内容なので、入力方式による抽出結果の違いも比較できます。

## Phase 5R のUAT資料回帰検証

求人票取り込み用のテキストとPDFを自動テストの対象にし、架空表記と主要な抽出対象項目が維持されていることを確認します。PDFはヘッダー、1ページ構成、5MB上限、埋め込みフォント、Unicode文字対応を検査します。

テストPDFに暗号化やJavaScriptが追加されていないことも確認し、レビュー担当者が安全な固定資料で取り込み導線を繰り返し確認できるようにしています。

## Phase 5S のPDFドラッグ＆ドロップ

求人票PDFは標準のファイル選択に加えて、枠内へのドラッグ＆ドロップでも指定できます。ドラッグ中は枠の色と背景が変わり、ドロップ後はファイル名と容量を表示します。

ドロップされたファイルにも既存のPDF形式、空ファイル、5MB上限の検証を適用します。読み取り中の差し替えは禁止し、ファイル自体をlocalStorageやデータベースへ保存しません。

## Phase 5T のTauriファイルドロップ互換性

Tauriのネイティブファイルドロップ処理をメインWebViewで無効化し、求人登録画面のHTML5ドラッグ＆ドロップへファイルを渡します。Tauri 2ではこの設定がない場合、特にWindowsでReactの`drop`イベントが届かないためです。

Candidate CRMはTauri独自のファイルドロップイベントを使用していないため、既存機能への影響はありません。設定値は自動テストで固定し、macOS・Windowsで同じReact処理とPDF検証を使用します。

## Phase 5U のPDF選択誤操作防止

複数の求人票PDFを同時にドロップした場合は、先頭ファイルだけを黙って使用せず「PDFは1件ずつ選択してください」と案内します。不正な複数選択は解除され、AI読み取りも実行できません。

選択済みPDFには個別の解除操作を表示し、テキストやURL、通常フォーム、読み取りキャッシュを消さずにPDFだけを選び直せます。読み取り中は解除操作も無効になります。

## Phase 5V のPDF内容事前確認

求人票PDFはAIへ送信する直前に先頭のPDF署名（`%PDF-`）を確認します。拡張子やMIMEタイプだけをPDFに偽装したファイルはクライアント側で拒否し、Edge FunctionやOpenAI APIを呼び出さないため、不要な利用枠と料金を消費しません。

この確認はファイル形式の簡易検証であり、ウイルススキャンではありません。サーバー側のサイズ・形式・内容検証も引き続き最終防御として使用します。

## Phase 5W のサーバー側PDF署名検証

クライアント側の検証を迂回してEdge Functionを直接呼び出した場合にも、アップロードされたPDFの先頭署名をサーバー側で再検証します。署名が不正なファイルは利用枠を確保する前、かつOpenAI APIへ送信する前に拒否します。

公開URLが`application/pdf`を名乗っていても内容にPDF署名がない場合は求人票として処理しません。逆に、正しいPDF署名を持つ公開ファイルはContent-Typeの誤設定に左右されずPDFとして扱います。

## Phase 5X の求人票キャッシュ指紋

画面内キャッシュは、テキスト・公開URL・PDF内容からWeb Crypto APIで生成したSHA-256指紋をキーにします。求人票本文やURLをキャッシュキーへそのまま保持せず、同じファイル名・容量・更新日時でも内容が異なるPDFを別の求人票として判定します。

指紋と最大3件の抽出結果は引き続きReactのメモリ内だけに保持し、localStorage、ファイル、Supabaseへ保存しません。ブラウザ標準APIだけを使用するため、macOS・Windowsで同じ処理になります。

## Phase 5Y の不完全PDF検出

PDF先頭の署名に加え、仕様上ファイル終端付近に必要な`%%EOF`マーカーを最後の2,048バイトから確認します。ダウンロードやコピーが途中で終わったPDF、PDF署名だけを付けた不完全ファイルは、OpenAIへ送信せず選び直しを案内します。

検証はデスクトップ側とSupabase Edge Function側の両方で行い、公開URL経由のPDFにも同じ条件を適用します。PDFの完全な修復やウイルススキャンを行うものではありません。

## Phase 5Z のパスワード保護PDF検出

PDF終端付近の`/Encrypt`辞書を確認し、パスワード保護されたPDFはAI実行前に拒否します。画面には「保護を解除したPDFを選択してください」と表示し、読み取れないファイルでAI利用枠や料金を消費することを防ぎます。

デスクトップ側を迂回したアップロードと公開URL経由のPDFもEdge Functionで再検証します。パスワードの入力、復号、解除済みファイルの自動作成は行いません。

## Phase 6A の未登録企業クイック登録

AI求人票取り込みで企業名を取得したものの登録済み企業へ完全一致しなかった場合、求人登録画面を離れず企業名だけを新規登録し、その企業を求人へ選択できます。企業は自動作成せず、担当者が取得名称を確認して「この企業を登録して選択」を実行した場合だけ作成します。

作成直前にも最新の企業一覧で正規化完全一致を確認し、同名企業が見つかった場合は新規作成せず既存企業を選択します。企業一覧の取得に失敗している間はボタンを無効化し、既存のadmin・agent向けRLSを通して登録します。

## Phase 6B の企業名確認・修正

未登録企業のクイック登録では、AIが取得した企業名を入力欄へ初期表示し、担当者が誤字、法人格、表記揺れを修正してから登録できます。空の企業名では登録できません。

新規作成しない場合は「既存企業から選ぶ」で通常の企業欄へ戻れます。修正後の名称を使って作成直前の重複確認を行うため、AI出力を無確認で企業マスタへ登録しません。

## Phase 6C の企業情報候補

求人票に業種や企業Webサイトが明記されている場合は、企業名と一緒にAIの候補として表示します。未登録企業のクイック登録欄で3項目を確認・修正し、担当者が登録操作を行った場合だけ企業マスタへ保存します。求人票に記載がない情報は推測しません。

WebサイトはHTTPまたはHTTPSの有効なURL形式を画面側で再検証し、不正な値のまま登録できません。企業名またはWebサイトが1社の登録済み企業と一致した場合は新規作成せず、既存企業を求人へ選択します。企業名とWebサイトが別々の既存企業に一致する場合は自動選択せず、担当者へ確認を求めます。

## Phase 6D の既存企業Webサイト照合

求人票の反映前確認でも、正規化した企業名に加えて有効なHTTP・HTTPSのWebサイトを既存企業との照合に使用します。企業名の表記が異なっていても公式サイトが一致する1社を特定できれば、照合理由を表示して既存企業を反映候補にします。

企業名とWebサイトが別々の企業に一致する場合や複数社へ一致する場合は、企業欄を自動変更しません。AI出力の不正なURLは照合に使わず、既存企業の選択または企業情報の修正を担当者へ求めます。

## Phase 6E の企業照合競合解決

企業名とWebサイトが別々の登録済み企業に一致した場合は、未登録企業の確認欄へ該当企業を一致理由付きで並べます。担当者は「企業名一致」「Webサイト一致」を比較し、正しい既存企業をその場で選択できます。

候補が表示されている間は新規企業の登録ボタンを無効化します。候補選択では企業マスタを更新・新規作成せず、求人フォームの企業欄だけを変更します。

## Phase 6F の反映前企業選択

企業照合が競合した場合は、AI読み取り結果の差分確認内に既存企業候補を表示します。担当者が正しい企業を選ぶまで反映ボタンを無効化し、選択後は企業欄を含む求人項目を一度に反映できます。

選択可能なのは企業名またはWebサイトが完全一致した候補だけです。画面から渡された企業IDは現在の候補一覧で再検証し、候補外のIDでは企業欄を変更しません。

## Phase 6G のAI抽出根拠表示

求人票から取得した項目には、AIが根拠にした原文の短い引用を差分プレビュー内へ表示します。担当者は反映後の値と求人票の記載を同じ場所で比較でき、推測や読み違いを登録前に見つけやすくなります。

引用は1件160文字、最大15件に制限し、説明やAIの推測を含めません。求人票本文、PDF、URL、引用、AI応答はデータベースやlocalStorageへ保存せず、求人登録画面のメモリ上だけで確認できます。

## Phase 6H の根拠未確認項目保護

AIが値を取得していても対応する原文引用がない項目には「根拠未確認」を表示します。その項目を反映対象に含める場合は、担当者が求人票を直接確認したことをチェックするまで反映できません。

反映対象を変更して未確認項目が増えた場合は確認状態を自動的に無効化します。企業変更に伴う採用担当者のクリアなど、AI抽出ではなく画面の整合性維持で発生する変更は対象外です。

## Phase 6I の根拠あり項目一括選択

差分プレビューの「根拠ありだけ選択」で、求人票原文の引用が確認できる項目だけを反映対象にできます。根拠未確認項目を手作業で一つずつ解除せず、安全側の内容だけを短時間でフォームへ移せます。

根拠付きの企業変更を選ぶ場合は、求人と採用担当者の所属整合性を守るため、以前の企業に属する採用担当者のクリアも一緒に選択します。選択と確認状態は画面内メモリだけで保持します。

## Phase 6J の取り込み元識別

読み取り結果の上部に、貼り付けテキスト、PDFファイル名、または公開URLのホスト名を「入力元」として独立表示します。複数の求人票を切り替えて確認する場合でも、現在表示している結果の出所を反映前に確認できます。

公開URLはパスやクエリを表示せずホスト名だけ、PDFはファイル名だけを表示します。入力元の本文や完全なURLを画面表示用メタデータとして永続化しません。

## Phase 6K の求人取り込み運用手順

Supabase Edge FunctionのSecret、デプロイ対象、JWT検証、架空データによるmacOS・Windows受け入れ確認をリリースチェックリストへまとめました。求人取り込み、候補者サマリー、AI利用状況の3関数を一組として確認します。

OpenAI APIキーだけをSupabase Secretへ置き、モデルIDはレビュー済みのサーバーコードで固定します。旧手順にあった`OPENAI_MODEL` Secretは使用せず、クライアントやCI成果物からモデル・秘密鍵を変更できない構成を維持します。
